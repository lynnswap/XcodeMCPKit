## [CONFIRMED] Missing MCP-Protocol-Version header is rejected with an unconditional 400 at HTTPHandler.swift:689-701, while the spec only recommends (SHOULD) assuming 2025-03-26 / relying on the negotiated version when the header is absent and reserves the 400 MUST for invalid/unsupported values; Docs/architecture.md:87 documents the strict behavior as contract.

EVIDENCE: Sources/XcodeMCPProxyKit/Internal/HTTPGateway/HTTP/HTTPHandler.swift:689-701 (validateExistingSession): `guard let protocolVersion = HTTPRequestValidator.protocolVersion(from: head.headers), protocolVersion.isEmpty == false else { _ = sendPlain(... status: .badRequest, body: "protocol version required" ...); return nil }`. This fires only after the session is confirmed to exist (665-675) and to have a stored negotiated version (676-688 `controlService.negotiatedProtocolVersion(id:)`), so the 400 is emitted precisely when the server DOES hold a negotiated version. Same pattern in validateDeletableSession:752-764. HTTPRequestValidator.protocolVersion is a bare `headers.first(name: "MCP-Protocol-Version")` (HTTPRequestValidator.swift:17-19); no earlier pipeline stage supplies a fallback (ProxyHTTPChildChannelInitializer.swift:29-40 adds only the NIO HTTP pipeline + HTTPHandler). Spec (2025-06-18 Transports, Protocol Version Header): "For backwards compatibility, if the server does not receive an `MCP-Protocol-Version` header, and has no other way to identify the version - for example, by relying on the protocol version negotiated during initialization - the server **SHOULD** assume protocol version `2025-03-26`." and "If the server receives a request with an invalid or unsupported `MCP-Protocol-Version`, it **MUST** respond with `400 Bad Request`." Refutation angle (a) partially holds and bounds severity: the SHOULD-assume-2025-03-26 clause is gated on "has no other way to identify the version," and here the server HAS a per-session negotiated version, so it is not violating that SHOULD. But the spec names "relying on the protocol version negotiated during initialization" as exactly the alternative the server could use, and provides NO clause authorizing 400 for a merely *absent* protocol-version header (the 400 MUST is scoped to "invalid or unsupported"; the explicit SHOULD-400 clause elsewhere is for a missing session id, not the protocol version). The behavior and doc contract are exactly as claimed; the deviation is stricter-than-spec (declines a spec-endorsed path) rather than a hard MUST violation.

## [REFUTED] ServerRequestTracker's 300 seconds is an upstream request timeout.

EVIDENCE: ServerRequestTracker.swift:27-33 uses `routeTimeout` only to calculate an `expiresAt` for response-ID route mappings. Expired entries are removed lazily when record/lookup/consume/complete is called; there is no scheduled timer, continuation failure, upstream cancellation, or generated response. Therefore the confirmed failure is that a buffered server request can be dropped without the proxy telling upstream. The upstream's actual wait duration is unknown and must not be stated as 300 seconds.
