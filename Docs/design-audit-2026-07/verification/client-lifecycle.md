## [REFERENCE ANALOG] `openai/codex@1f0566d3` demonstrates typed session-expiry, single-flight recovery, and one-shot replay, but not a shared logical deadline or pagination handling.

EVIDENCE: `codex-rs/rmcp-client/src/http_client_adapter.rs:60-67,87-164,285-350` types session-ID POST/GET 404 as `SessionExpired404`. `codex-rs/rmcp-client/src/rmcp_client.rs:105-143,324-333` owns the transport recipe, initialize context, service identity, and recovery semaphore. BOUNDARIES: Codex starts a fresh per-attempt timeout for replay and uses a separate initialize timeout (`rmcp_client.rs:987-1007,1025,1165-1169`), so it is not the desired one-logical-deadline model. Its transient classifier includes string parsing (`streamable_http_retry.rs:144-153,168-182`), which is not a typed-contract precedent. Low-level tools/list retains `next_cursor`, but the real upper consumer discards it (`codex-rs/rmcp-client/src/rmcp_client.rs:512-546`, `codex-mcp/src/rmcp_client.rs:575-612`), so it is not a pagination analog. Its `Connecting / Ready / Closed` state is private (`rmcp_client.rs:105-114,716-722`) and does not establish a public connection-state contract. GET 404 is typed, but request recovery catches the send-operation error path; this does not prove that Codex recovers an SSE GET 404 through the same path.

DESIGN CONSTRAINT FOR XCODEMCPKIT: a shared session-lifecycle owner should classify only a request that actually carried `Mcp-Session-Id` as `.sessionExpired`, recover single-flight by failed transport/session identity, initialize a fresh session, and replay at most once only when delivery-before is proven. Initial send, lock wait, initialize, `notifications/initialized`, and replay must share one absolute deadline. The spec MUST requires starting the new session; transparent replay is a separate product contract.

## [WEAKENED] The SDK uses a fixed 60s default timeout with no per-call override; progress-based reset is spec MAY, while per-request configurability is the genuine SHOULD gap.

EVIDENCE: The normative attribution is wrong: the lifecycle page (2025-06-18 basic/lifecycle, Timeouts) says, verbatim: "Implementations **MAY** choose to reset the timeout clock when receiving a progress notification corresponding to the request, as this implies that work is actually happening. However, implementations **SHOULD** always enforce a maximum timeout, regardless of progress notifications..." — MAY, not SHOULD, so not resetting on progress is spec-permitted, not a violation. The mechanical facts are all confirmed: Sources/XcodeMCPKit/Internal/ClientRuntime/InitializedMCPClientSession.swift:263-284 withRequestTimeout races the operation against clock.sleep(requestTimeout) with no reset hook; the progress path (handleMessage lines 306-343, progress branch 323-339) never touches timeout state; default is .seconds(60) at Sources/XcodeMCPKit/XcodeMCP.swift:138; callTool (XcodeMCP.swift:289-320) and request (337-342) and session.request (InitializedMCPClientSession.swift:118-122) accept no per-call timeout. The genuine SHOULD-level gap is a different sentence: "SDKs and other middleware **SHOULD** allow these timeouts to be configured on a per-request basis." — the SDK only offers a per-client XcodeMCPConfiguration.requestTimeout (XcodeMCP.swift:121, 138). So: code behavior CONFIRMED, but the claimed spec violation (progress reset) is refuted at the normative level and should be re-anchored to the per-request-configurability SHOULD.

## [CONFIRMED] Task cancellation does not send notifications/cancelled upstream; the string is absent from Sources; the spec normative level determines whether this is a violation or usability gap.

EVIDENCE: Factual part confirmed: `rg -n "notifications/cancelled" Sources` returns no matches (exit 1) across the entire repo Sources tree; Sources/XcodeMCPKit/Internal/ClientRuntime/InitializedMCPClientSession.swift:172-174 onCancel only does pendingRequests.fail(idKey:, error: CancellationError()) — purely local, nothing is sent upstream. Normative split per spec: (a) For caller-initiated Task cancellation, the cancellation page (2025-06-18 basic/utilities/cancellation) is descriptive: "Either side can send a cancellation notification to indicate that a previously-issued request should be terminated." — no MUST/SHOULD attaches to sending, so this is a usability gap (the server keeps processing an abandoned request), not a spec violation. (b) For the timeout path it IS a SHOULD-level deviation: lifecycle Timeouts says, verbatim: "When the request has not received a success or error response within the timeout period, the sender **SHOULD** issue a [cancellation notification] for that request and stop waiting for a response." — withRequestTimeout (InitializedMCPClientSession.swift:263-284) throws requestTimedOut and stops waiting but never issues notifications/cancelled. The receiver-side SHOULDs (stop processing, free resources, not respond) and "sender SHOULD ignore any response... that arrives afterward" are unaffected by the absence (late responses find no pending continuation after fail()).
